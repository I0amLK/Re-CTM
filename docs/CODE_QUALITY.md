# Re-CTM 代码质量与功能优先规范

> **一句话原则：只做能够以功能正确性、安全边界、可靠性、可维护性或可验证性能收益证明价值的最小代码改进。**

本规范用于代码清理、重构、去重、模块拆分、性能优化和技术债治理。它不是为了追求抽象、格式统一、文件变短或“看起来更现代”，而是为了让 Re-CTM 的功能更可靠、更容易验证、更安全地继续演进。

## 1. 决策优先级

发生冲突时，按以下顺序决策：

1. 数学工作流、OAuth、MCP、Native 隔离和持久化行为的正确性；
2. L0/L1/L2 权限边界、私有状态、能力句柄和最终化门禁的安全性；
3. 用户可见功能、协议兼容性和错误恢复语义；
4. 可测试性、可观察性和故障定位能力；
5. 可维护性与局部复杂度；
6. 有测量证据支持的性能；
7. 纯粹的格式、命名或审美偏好。

低优先级目标不得破坏高优先级目标。仅有“代码更漂亮”“文件更短”“抽象更统一”不是可执行优化理由。

## 2. 优化项目准入门槛

任何优化在开始修改代码前，必须写入 `code-optimization-graph.json`，并至少说明：

- 当前存在的具体问题或风险；
- 可观察、可测试的功能收益；
- 证据，包括失败案例、重复逻辑、复杂度数据、性能基线或协议漂移记录；
- 修改范围和明确的非目标；
- 验收标准与验证命令；
- 风险、依赖、停止条件和回滚办法；
- 状态、优先级和执行顺序。

缺少上述任一核心信息的项目只能保持 `proposed`，不得进入代码实施。

以下情况默认拒绝：

- 没有已观察问题的微优化；
- 全仓库无差别格式化或批量改名；
- 仅为减少行数而引入间接层；
- 为单个调用点增加没有边界价值的抽象；
- 没有兼容计划就删除隐藏旧协议、迁移路径或错误码；
- 没有基线和目标就宣称性能提升；
- 将安全检查移出原有信任边界以换取代码简洁。

## 3. 最小必要改动

- 优先修复根因，不在多个调用点重复打补丁。
- 优先小范围、可回滚、可独立验证的改动。
- 不在同一个补丁中混合功能修改、无关重命名和大面积格式化。
- 代码移动必须保留历史可审查性；除非确有必要，不同时改写移动代码的全部风格。
- 新抽象必须至少满足一项：消除会导致行为漂移的重复、建立明确的信任边界、形成可测试的纯逻辑单元，或稳定公共协议。
- 模块或函数很长只是调查信号，不是自动拆分理由。拆分后必须更容易验证功能，而不是把控制流分散到更多文件。

## 4. Python 代码规范

### 4.1 语言与兼容性

- 目标版本为 Python 3.11 及以上，与 `pyproject.toml` 保持一致。
- 优先使用标准库。新增依赖必须写明功能收益、供应链风险、部署影响和移除方案。
- 不使用依赖运行时全局 monkey patch 的实现。

### 4.2 类型与数据边界

- 公共函数、跨模块接口、持久化入口和工具处理器必须有参数与返回类型。
- 动态 JSON 边界可以使用 `Mapping[str, Any]`，但必须在进入核心逻辑前完成结构验证。
- 不通过 `str(value)`、`int(value)` 等隐式转换掩盖非法协议输入；只有明确允许转换的内部持久化兼容路径可以这样做，并须有测试。
- 结构稳定的数据优先使用 dataclass、枚举或明确的 schema；不要在核心逻辑中依赖未声明的字典键。
- `None`、空字符串、缺失字段和空数组必须有明确且一致的语义。

### 4.3 函数与模块

- 函数应有单一可描述责任；校验、状态计算、I/O 和序列化尽量分层。
- 超过约 80 行的函数应检查是否能提取纯校验、纯计算或状态分支；超过约 150 行的函数必须在优化图中记录审查结论，但不要求机械拆分。
- 超过约 1000 行的模块应检查职责是否仍然内聚。模块拆分必须保留一个明确的权威入口，避免形成新的双重实现。
- 嵌套分支优先通过早返回、状态表或独立纯函数降低认知负担，但不得隐藏权限和事务顺序。
- 不用布尔参数组合隐式编码多个业务模式；已有公共接口除外，新增模式优先使用枚举或具名配置。

### 4.4 命名、格式与注释

- 名称描述业务事实，不描述临时实现技巧。
- 私有帮助函数使用 `_` 前缀；常量使用全大写；错误码和状态值保持稳定。
- 优先保持行宽便于审查，通常不超过 100 至 120 字符；不要仅为行宽制造难读的多层包装。
- 注释解释“为什么、边界和不变量”，不复述代码。
- TODO 必须关联 `OPT-*`、风险项、测试或明确 issue；无归属 TODO 不得长期留在源码。
- 不执行全仓库格式化作为独立优化项目。

## 5. 架构与权威来源

- L0 OAuth、L1 Native mode、L2 workflow capability 三层权限不可合并或相互继承。
- 18 个 CTM Native 工具前缀、6 个公开 Rethlas façade、隐藏兼容别名和 workflow protocol 兼容性属于公共功能约束。
- 状态转换、权限规则、工具 schema、错误恢复和持久化迁移各自应有单一权威来源。
- 同一业务规则如果必须在文档、schema、运行时和测试中重复，必须有机械一致性检查或明确生成关系。
- Native workspace、数据根目录和 private vault 的隔离不得为了代码复用而弱化。
- 最终证明、项目 VERIFIED/CONDITIONAL revision 和 reference audit 的机械门禁不得改成模型可控流程。

### 文档职责边界

- `README.md` 面向使用者，说明安装、连接、公共工具和日常工作流；不要塞入内部实现账本。
- `docs/DEPLOYMENT.md` 面向部署/operator，说明信任边界、升级、目标机验收与故障排查。
- `AGENTS.md` 面向维护者和编码 agent，记录不可违反的工程/安全不变量。
- `docs/CODE_QUALITY.md` 只负责清理、重构和优化治理规则。
- `engineering-graph.json` 是机器可审计的架构/安全关系图；`project-progress.json` 是历史决策与验证账本。
- 稳定事实可以为不同受众重复摘要，但版本、公共工具数量、验证边界和关键链接必须由机械检查防止漂移。

## 6. JSON 与 MCP contract 规范

- 对象 schema 必须明确 `type`、`required` 和 `additionalProperties` 策略。
- `oneOf`/`anyOf` 分支必须自包含；operation/action 分支应互斥并拒绝无关字段。
- schema 中的默认值、处理器中的默认值和文档示例必须一致。
- 每个模型参与的 task 必须继续提供 `write_contract`、`commit_action`、`commit_payload_schema` 和合法示例或模板。
- 示例必须通过与运行时相同的 schema 校验器。
- capability 是不透明句柄，不能解码、编辑、规范化、拼接或合成；`run_id` 与 capability 必须来自同一个当前 task envelope。
- JSON 文件必须使用 UTF-8、稳定字段名、明确 schema version，并通过专用 validator。
- 不在可发布 manifest、debug bundle 或日志中写入 OAuth secret、capability、问题正文、证明正文或私有推理。

## 7. 错误处理与可观察性

- 预期业务失败使用 `ReCTMError`，保持稳定的 `code`、`category`、`retryable` 和结构化 details。
- 只在工具、HTTP、进程等真正的系统边界捕获通用 `Exception`；边界内应保留具体异常。
- 不把 permission/security failure 转换成 recoverable validation failure。
- 日志记录 trace ID、状态、动作和经过脱敏的事实，不记录原始 secret 或 capability。
- 新错误路径必须说明客户端应停止、重试、修正输入还是恢复任务。

## 8. 持久化与事务

- schema 迁移必须版本化、可重复验证、事务化，并对更新版本数据库 fail closed。
- 一次业务原子操作必须在一个清晰事务边界内完成。
- 不把外部网络、LaTeX 编译或任意执行放进持有写事务的长生命周期区间。
- VERIFIED revision、final artifact、reference audit 和 project promotion 的幂等与并发规则必须有回归测试。
- 重构 storage 层前先建立旧数据迁移、失败回滚和并发冲突基线。

## 9. 安全边界代码

- 权限校验、路径解析、能力验证、隔离 attestation 和 secret redaction 代码优先显式，不追求过度抽象。
- 安全检查的顺序是功能的一部分；重排前必须证明不会产生写入、信息泄漏或错误恢复副作用。
- 外部输入在最外层校验，内部帮助函数仍需维护关键不变量，不能只依赖调用者自律。
- 高风险重构必须有负向测试，包括拒绝路径、跨 owner/run/domain 混用、stale/revoked token 和越界路径。

## 10. 测试规范

- 修复缺陷必须先补充或同步加入可复现的回归测试。
- 行为保持型重构必须证明公共返回、错误码、状态转换、持久化结果和安全拒绝语义不变。
- 纯函数使用单元测试；跨层功能使用集成测试；目标机器、浏览器、真实 OAuth、真实 CAS/LaTeX 继续保留人工验收边界。
- 不以 mock 通过证明真实隔离、真实外部检索或真实浏览器兼容。
- 每个优化项目至少运行其专属验证命令，并在完成前运行：

```bash
python3 scripts/run_local_checks.py
```

- 本地通过只证明确定性本地行为，不得自动把 manual validation 标为完成。

## 11. 性能优化规范

- 先记录可重复基线、输入规模、环境、瓶颈和用户影响，再提出性能优化。
- 优化目标必须量化，并同时设置正确性和内存/资源上限。
- 不牺牲权限校验、事务原子性、错误信息或可审查性换取未经证实的速度。
- 性能未成为功能瓶颈时，相关项目应保持 `rejected` 或 `proposed`，不得抢占正确性工作。

## 12. 删除、兼容与弃用

- 删除代码前证明无运行引用、无持久化数据依赖、无隐藏兼容调用和无文档承诺。
- 兼容入口必须有使用证据和退出条件；不能因为“旧”就立即删除。
- 弃用需要稳定告警、迁移说明、测试和版本边界。
- 删除 generated、validation 或 evidence 文件前确认它们是否是发布与人工验收记录。

## 13. 优化状态与执行规则

状态使用：

- `proposed`：问题已记录，但证据或方案尚不足；
- `approved`：准入信息完整，可以开始；
- `in_progress`：正在实施，必须保持单一明确目标；
- `blocked`：存在外部或验证阻塞，必须记录 blocker；
- `completed`：验收通过并已写执行回执；
- `rejected`：证据不足、收益不成立或风险不值得；
- `superseded`：已被新的优化项目替代。

执行前把状态改为 `in_progress`。执行中发现功能收益不成立，应立即停止并改为 `rejected`，而不是扩大范围寻找理由。

## 14. 执行回执规则

`code-optimization-graph.json` 中的 `receipts` 是追加式事实记录。回执不得覆盖历史结论或仅写“已清理”。每个完成项目必须记录：

- 优化项目 ID、起止时间和状态变化；
- 原始功能问题与最终功能结果；
- 实际修改文件；
- 执行命令、退出码和结果摘要；
- 测试与人工边界；
- 行为前后对比；
- 安全、兼容、性能和数据迁移风险审查；
- 回滚方法；
- 未解决事项；
- `accepted`、`rejected` 或 `partial` 决策。

规则：

1. `completed` 必须有 `accepted` 回执，且至少一个成功验证命令；
2. `rejected` 必须有拒绝原因回执，不能悄悄从 TODO 删除；
3. `blocked` 必须记录 blocker 和恢复条件；
4. 测试失败时不得把状态写成 `completed`；
5. 只有实际运行过的命令才能写进回执；
6. 不能用“测试通过”替代具体命令和退出码；
7. 回执中的本地验证不得冒充目标机器或真实网页验收；
8. 若回滚会破坏后续数据或迁移，必须在实施前停止并重新设计。

## 15. 完成定义

一个优化项目只有同时满足以下条件才算完成：

- 功能目标仍然成立，并有可观察证据；
- 变更范围没有无关扩张；
- 公共协议、安全边界、持久化和兼容性已审查；
- 项目验收标准全部满足；
- 专项测试与 `run_local_checks.py` 通过；
- 文档和优化图已同步；
- 执行回执已追加；
- 未完成的人工验收被明确保留为 pending。
